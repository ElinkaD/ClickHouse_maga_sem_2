## Лабораторная №1: SCD в ClickHouse

Ориентир: [задание по SCD в ClickHouse](https://github.com/sitnikovik/abds/blob/master/lab/01/README.md). Проект содержит ClickHouse, схему из семи таблиц, генератор и загрузчик CSV, а также Python HTTP-сервис.

### Запуск

```sh
make run
make setup
make services
```

`make run` запускает один контейнер ClickHouse и Python HTTP-сервис. `docker-compose.yml` подключает описание сервисов из `compose.services.yml` с параметрами из `.env.local`, поэтому команды `docker compose logs` и `docker compose down -v` также работают без флага `--env-file`. При первом запуске с пустой папкой `volume/` контейнер создаёт базу `energosbyt` и выполняет все файлы `sql/ddl/*.sql`. `make setup` повторно создаёт недостающие таблицы, генерирует CSV и загружает их. Данные ClickHouse сохраняются в локальной папке `volume/`.

Команды по отдельности:

```sh
make schema
make gen
make load
make teardown
make test
make stop
```

`make gen` создаёт семь файлов `data/<table>.csv` без заголовка. Порядок полей совпадает с DDL. Генератор использует фиксированный seed, поэтому при повторном запуске данные получаются одинаковыми. `data/` и `volume/` не коммитятся. `make load` проверяет наличие всех CSV, очищает таблицы и затем загружает файлы потоково через HTTP-интерфейс ClickHouse. Повторный вызов `make load` не накапливает дубли. При ошибке в середине загрузки вызовите `make load` ещё раз: он снова начнёт с пустых таблиц. `make teardown` удаляет таблицы и данные, оставляя пустую базу; после него `make setup` создаст всё заново.

Ожидаемые объёмы после `make gen`:

| Таблица | Строк |
| --- | ---: |
| `dim_realty` | 1 000 |
| `dim_gauges` | 1 051, включая резервный счётчик `id = 2` |

### HTTP API

Реализация находится в `app/handlers.py`, маршрутизация — в `app/server.py`. Ответы и ошибки соответствуют [контракту ТЗ](https://github.com/sitnikovik/abds/blob/master/lab/01/README.md#http-сервис). Примеры запросов находятся в `api/energosbyt.postman_collection.json`. Все SQL-значения передаются через типизированные параметры ClickHouse вида `{id:UInt64}`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/ping` | Проверка сервиса, пустой ответ `200` |
| `GET`, `PATCH` | `/users/{id}` | Чтение и изменение собственника (SCD 1 и 3) |
| `GET` | `/realty/{id}` | Объект недвижимости |
| `POST`, `GET` | `/realty/{id}/readings` | Передача показания и чтение за период |
| `GET` | `/realty/{id}/invoices` | Счета с пагинацией |
| `GET` | `/tariffs?date=YYYY-MM-DD` | Версия тарифа на дату (SCD 2) |
| `POST` | `/realty/{id}/gauges` | Отмена старой и новая установка счётчика |

Проверки обработчиков без ClickHouse: `make test`. Для полной проверки нужны `make run`, `make setup` и работающий Docker.

Для быстрой проверки используйте [Postman-коллекцию](api/energosbyt.postman_collection.json). В коллекции 23 запроса с проверками статусов и полей ответа. Порядок важен: сначала идут обычные запросы и изменения SCD, затем примеры ошибок. Коллекция изменяет данные объекта и собственника с `id = 1`; перед повторением с исходным состоянием выполните `make setup`.

SQL-запросы для всех сценариев SCD и удаления ошибочной строки — в [docs/scd.md](docs/scd.md).

### Выбор ключей и партиционирования

| Таблица | Ключ сортировки | Причина |
| --- | --- | --- |
| `dim_realty`, `dim_gauges`, `dim_users` | `id` | Быстрый поиск объекта по идентификатору. Для `dim_users` все версии одного собственника имеют один ключ замены. |
| `dim_tariffs` | `(id, valid_from)` | Разные интервалы одного тарифа сохраняются, а исправленная версия того же интервала заменяет прежнюю. |
| `fact_gauge_bindings` | `(realty_id, gauge_id)` | Установка и аннулирование одного счётчика имеют одинаковый ключ; `version` и `sign` позволяют движку свернуть пару. |
| `fact_meter_readings` | `(realty_id, reading_date)` | Корректировка показания за тот же день заменяет прежнее независимо от изменившихся `user_id`, `gauge_id` или `tariff_id`. |
| `fact_invoice` | `(realty_id, created_at)` | Счета объекта читаются по времени выставления. |

Показания разделены по месяцам `reading_date`: весь трёхлетний период содержит около 1,1 млн строк, и запросы за период читают только нужные месяцы. Дата показания у корректировок остаётся той же, поэтому все версии попадают в одну партицию. Небольшие измерения и счета не партиционируются, дробление их на множество мелких частей бесполезно.

`ReplacingMergeTree` и `VersionedCollapsingMergeTree` применяют замену и свёртку во время фоновых слияний, поэтому в запросах к таблицам, которые используют этот движок, применяется `FINAL`. Для `dim_tariffs` новая версия периода должна иметь новый `valid_from`, а исправление уже существующей версии — тот же `valid_from` и более поздний `updated_at`.

Для отмены установки счётчика нужно записать `sign = -1` с теми же `realty_id`, `gauge_id` и `version`, что и у установки `sign = 1`. Повторная установка после отмены получает `version + 1`. Исправление показания за день вставляется с теми же `realty_id` и `reading_date`, но более поздним `created_at`; прежняя строка остаётся до фонового слияния.

## Настройка репозитория

### Защита основной ветки

После создания репозитория из шаблона **обязательно настройте правила защиты для ветки `main`**:

1. Откройте **Settings** → **Branches** → **Add classic branch protection rule**
2. В поле **Branch name pattern** укажите: `main`
3. Включите следующие опции:
   - **Require a pull request before merging**
     - Require approvals: **1**: требует минимум одного одобрения перед слиянием
   - ***Require status checks to pass before merging***
     - Выберите *"autograder"*: проверит все лабораторные работы автоматически
     - ***Require branches to be up to date before merging*** (рекомендуется):
     требует, чтобы ветка PR была синхронизирована с последними изменениями из основной ветки перед слиянием
   - ***Do not allow bypassing the above settings***: запрещает обход настроек защиты ветки
4. Нажмите **Create** или **Save changes**

> ⚠️ **Важно:** Без этих настроек автоматические проверки не будут блокировать PR с ошибками.

### Добавление коллабораторов

Чтобы преподаватели могли проводить код-ревью:

1. Откройте **Settings** → **Collaborators**
2. Нажмите **Add people**
3. Добавьте всех кто есть в списке ревьюеров в файле [CODEOWNERS](CODEOWNERS)
4. Выберите роль: **Write** (или выше), иначе ревьюер не сможет одобрить PR
